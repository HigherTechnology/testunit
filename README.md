

# TestUnit & Philosophy

I use unittest heavily in my projects and favor object oriented testing as well as object-oriented code in general. A TestCase is a test and one fixture put together as you see with setUp and tearDown before every test method. The unittest module scales well from unit test to acceptance test and in my opinion and preference it is better to have everything available on a class you inherit. Regardless to what method is best what can be said for sure is that in following the unittest testing style there are patterns of usage yet to be discovered and stuff that could be added onto it to make this testing style more powerful. 

**Why use unittest.TestCase/unittest.IsolatedAsyncioTestCase**
- You can write a fixture in your IDE with an ergonomical selection/completino of setUp and tearDown.
- You can pair them with pytest to write your own custom suited ergonomic TestCases. You can have a complex setup on a base class using pytest fixtures and then inheriting classes can have their own setUp/tearDown to fill in conveniently. 
- You can favor writing code directly to get the behavior you want rather than relying on plugins and obscure conftest.py files. For example, you could create a benchmarking class based on the inherit_subclasses method, replacing the methods of inheriting classes with ones that measure the time taken to execute and pass/fail while allowing for writing tests exactly like normal.

- You can write asynchronous tests with zero configuration or dependencies.

## Philosophy

This library is intended for people who would like to use object-oriented and code heavy testing. Features and extensions should be written in the form of base classes or decorators or both if possible. It is better to have something on a base class than to import it. Modifying attributes of a class should be favored over parameterization -- Which there isn't strictly a strong preference for but with certain test naming styles there isn't much room for parameters and they may not integrate with with unittest.TestCase classes.

- **Composition is not better than inheritance:** There is exceptional value in being able to define a class which gives you everything you need for testing something and then the only thing you have to do is inherit it. There is a strong immaturity surrounding many communities and inheritance, for example, google go doesn't have it because juniors might abuse it, which is essentially saying that we can't have testing like this (steak) because a baby can't chew (can't use inheritance without making a mess).
- **Inversion of Control through inheritance:** A test may require an object setup to interact with an API to test response fields. The test should not be in control of setting this up, where should it come from and what do we know is best practice? We should invert the control of dependency creation to something higher up (usually ending at the entry point), by saying that you require something, something else can give it to you and you separate the concern of where it comes from to elsewhere, you can change what your code is given and your tests remain the same -- In this case your base class is your entry point and you can decouple your test from dependency creation via inheritance.
  - Simply write a base class with everything your test requires, have the class containing your tests inherit from it, your tests couple to attributes or methods which are inherited, you can change these by changing the base class. Design Principles should not be applied like cardboard cutouts in areas like automated testing. I'd go as far as to say that inheritance may be superior to a dependency injection framework in this case as you never have to specify dependencies in your tests to get them.
- **The power of unittest is in it's constraints**: It is powerful because it is simple and anything added onto it shouldn't be significantly more complicated than the base library is. For example with fixtures: A TestCase class is constructed with each method on the class, the setUp/tearDown are a fixture, a TestCase instance is fixture + test.  A fixture may also has assertion methods to make it easier to write tests. **A simple addition of independent fixtures:** You can have fixtures by adding a base class with setUp and tearDown methods, you can have tearDown called on ``__del__`` and setUp in constructor.
  - **Additions will be familiar and ergonomic**: When you inherit TestCase and go to add a setUp and or tearDown your IDE will suggest to you to fill in, the new fixture class will do the same and uses the sameCasing. Instead of TestCase you inherit Fixture and can use your fixture in any TestCase. 
- **Writing tests should be convenient**: This isn't unique to this library or object-oriented testing, it also applies to all types of testing but is something to highlight as patterns and elements of this approach should be used to make it so. The unittest test case class provides several assertion methods and notably: You don't have to write your own assertion methods to get the right input and you can rely on them to do the right thing with the given input.
  - **You can use fixtures to make writing tests convenient**. For example, if you have tests that need  a temporary file and to verify something was written to it, you can create a TemporaryFileFixture that will give you a path to a temporary file with an assertFIleContentsEqual("string") method. You instantiate your fixture, are given what you need, it will clean its self up and you can use convenient methods on it to assert what you want on your tests.
- **Different Base class setups over parameterization**: The class should be setup for the tests to run with rather than parameterizing them through methods. Stances on this are subject to evolution and patterns need figured out for parameterization patterns and alternatives more broadly.
- **Test Boundaries/public & private code**: Code should be written with intent and tested by it. For example: You can write code with the intent that specific functions and classes are what should be used publicly and anything internally supporting them including other functions and classes are an implementation detail. Python doesn't necessarily have public/private stuff but if you name something with an underscore it indicates it's meant only to be used internally. By being particular about what is public and what is an implementation detail you can create boundaries that you test at to allow for strong refactoring capability.
